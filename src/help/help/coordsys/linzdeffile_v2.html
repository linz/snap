LINZ deformation file format version 2

Version 2 of the LINZ deformation file format replaces version 1's single-reference-date, per-component zero/fixed/interpolate rule with a more flexible per-component time model, and adds nested sequences. There is no DATA_TYPE in version 2 – every sequence works the same way, and each component instead chooses its own time model: either PIECEWISE_LINEAR, which scales the component's value directly at each date, or VELOCITY, which treats the component's value as a rate to be integrated into a displacement – see the TIME_MODEL record below.

Set FORMAT to LINZDEF2L (little-endian) or LINZDEF2B (big-endian) in the header to select this version – see the shared header section for the other header records.

Dates on this page are formatted as dd-mmm-yyyy, for example “20-Jan-2004”, optionally followed by a time such as “12:30”.

Model header records

In addition to the shared header records, version 2 requires the same model-level records as version 1:

Code

Type

Description

VERSION_NUMBER

number

The version of the deformation model – digits, optionally with a single decimal point (eg “1.0”).

VERSION_DATE

date

A human-readable record of when this version became authoritative. SNAP does not use this value in any calculation – it is descriptive only.

DESCRIPTION
text ...
END_DESCRIPTION

text

A free-form, multi-line description of the model. Any text is accepted, up to the terminating END_DESCRIPTION line.

These header records, together with the shared ones, may appear in any order, except that DEFORMATION_MODEL must be the first record in the file, and FORMAT must appear before the first DEFORMATION_SEQUENCE record.

Sequence records

Each deformation sequence section should contain the following records:

Code

Type

Description

DEFORMATION_SEQUENCE

string

The name of the sequence (eg National model, Arthurs’ Pass earthquake).

DIMENSION

1, 2, 3

The dimension of the deformation (1 = height only, 2 = horizontal only, 3 = 3d deformation).

START_DATE

date

The first date at which the sequence applies – it is assumed to be zero before this.

END_DATE

date

The last date at which the sequence applies – it is assumed to be zero after this date.

ZERO_BEYOND_RANGE

string

Either “yes” or “no”. If “yes”, the sequence contributes zero for points beyond the spatial extent of its components. If “no”, evaluating a point beyond that extent fails with an error – and since the model's total deformation is the sum of every sequence, that error aborts the whole calculation, not just this sequence's contribution. If omitted, defaults to “yes”.

NESTED_SEQUENCE

string

Either “yes” or “no”. If “yes”, only the first component of the sequence (in sequence order) whose own spatial extent includes the evaluation point is used, and every other component of the same sequence is ignored. If “no”, every component of the sequence that covers the point is evaluated and all of their contributions are added together. Nesting only affects this one sequence's own components – every other sequence in the model is still added in as usual regardless of whether it is nested. If omitted, defaults to “yes”.

DESCRIPTION
text ...
END_DESCRIPTION

text

A free-form, multi-line description of the sequence. Any text is accepted, up to the terminating END_DESCRIPTION line.

Because NESTED_SEQUENCE defaults to “yes”, a sequence with several components that are meant to all contribute together (rather than only the first match) must set NESTED_SEQUENCE no explicitly – omitting it silently nests the sequence instead.

Type

Either “grid” or “trig”.

DESCRIPTION
text ...
END_DESCRIPTION

text

A free-form, multi-line description of the component. Any text is accepted, up to the terminating END_DESCRIPTION line.

The TIME_MODEL record

TIME_MODEL never specifies a deformation value directly – it always works together with the fixed spatial pattern already defined by the component's own grid or trig file. There are two forms (case insensitive), each using the same list-of-dates syntax (dates in the same dd-mmm-yyyy form used throughout this file, converted internally to a decimal year for the calculation) but combining with the component's value in different ways:

Form

Syntax

PIECEWISE_LINEAR

PIECEWISE_LINEAR f0 d1 f1 ... dn fn

VELOCITY

VELOCITY v0 d1 v1 ... dn vn (or bare “VELOCITY” with no parameters at all)

 

PIECEWISE_LINEAR

TIME_MODEL only computes factor(time). Call the component's own grid or trig value at a given point G (it does not change over time). The deformation this component contributes, at a point and a time, is:

deformation(point, time) = factor(time) × G(point)

f0 gives factor(time) at and before d1; fn holds it constant after dn; and between any two consecutive listed dates di/fi and di+1/fi+1, the factor interpolates linearly:

factor(time) = fi + [(time − di) / (di+1 − di)] × (fi+1 − fi)

Since G is a fixed number for a given point, and the factor is linear between di and di+1, deformation(point, time) is also a straight line between those two dates, running from fi × G(point) at di to fi+1 × G(point) at di+1. This holds for every consecutive pair in the list, so the whole curve – across all of d1...dn – is a series of straight-line segments joined at each listed date, each with its own slope: a genuine piecewise linear function of time, exactly as this form's name says.

A ramp, not a step, is what happens between any two distinct dates – there is always some elapsed time to interpolate across. A step instead needs zero elapsed time to ramp across, which happens in one of two ways: a component with only one listed date has nothing to ramp towards, so it jumps straight from f0 to that single f1 the instant d1 passes (as in the second worked example below); or two consecutive dates in the list can be given as the same date, giving that particular ramp zero width so it happens instantaneously at that shared date, while still allowing further ramps to or from it.

VELOCITY

VELOCITY has the same shape as PIECEWISE_LINEAR's own syntax – except that v0...vn are rates instead of values. Turning those rates into actual displacement values means integrating them, and integration needs a start and end point to anchor the accumulation: this uses the sequence's own START_DATE and END_DATE. So call the full list of dates D0...Dn+1, where D0 = START_DATE, D1...Dn = d1...dn, and Dn+1 = END_DATE. Rate vk applies for the gap between Dk and Dk+1.

First, integrate: accumulate a running total by adding each rate's contribution over its own gap – this is the actual “integration”. Call this running total f′, a factor value in its own right, just not yet re-centred:

f′0 = 0

f′k = f′k-1 + (Dk − Dk-1) × vk-1   for k = 1...n+1

Second, re-centre: find whichever gap REF_DATE falls into – call it segment j, so Dj ≤ ref_year < Dj+1 – and work out f′ at REF_DATE itself, partway through that segment. Subtracting it from every f′k shifts the whole curve so it is exactly zero at REF_DATE:

offset = f′j + (ref_year − Dj) × vj

fk = f′k − offset   for every k

Once f0...fn+1 are worked out at D0...Dn+1, they are used exactly as PIECEWISE_LINEAR's own fi/di pairs are in the formula already given above: f0 holds before D0, fn+1 holds after Dn+1, and every gap between them interpolates linearly. There is no way to give a VELOCITY component a non-zero displacement at its own reference date, since the re-centring step always forces it to zero there by construction.

Bare “TIME_MODEL VELOCITY” is the case with no d/v pairs at all, so n=0: a single rate v0=1.0, spanning the whole sequence from D0=START_DATE to D1=END_DATE. Working through both steps above: V0=0, V1=D1−D0; offset = ref_year−D0; so f0 = D0−ref_year and f1 = D1−ref_year. Interpolating between those two with the same PIECEWISE_LINEAR formula used above gives:

factor(t) = t − ref_year

– a straight line through zero at REF_DATE, slope 1, matching the single rate of 1.0. If the grid or trig file holds an actual velocity (say, mm/year), this is exactly what turns elapsed years into an accumulated displacement in mm.

Worked example

The example on the LINZ deformation file format page has a national velocity model (a single component with the bare TIME_MODEL VELOCITY form) and a Fiordland earthquake sequence with two trig components, each with its own PIECEWISE_LINEAR time model. Here is how those two components' own factors play out at specific dates.

The first component (fiordland_20090715_a.trg) has REF_DATE 15-Jul-2009 and TIME_MODEL PIECEWISE_LINEAR 0.0 15-Jul-2009 0.8 20-Jul-2009 1.0. The initial factor (0.0) applies up to and including the first listed date, so this is not a single smooth ramp: it is an instant step from 0.0 to 0.8 exactly at 15-Jul-2009, immediately followed by a five-day ramp from 0.8 up to 1.0:

Date

Factor

Before, and at, 15-Jul-2009

0.0

Immediately after 15-Jul-2009

0.8

17-Jul-2009 (interpolated)

0.88

20-Jul-2009 and after

1.0

The second component (fiordland_20090715_b.trg) has the same REF_DATE but only one listed date, TIME_MODEL PIECEWISE_LINEAR 0.0 15-Jul-2009 1.0 – with nothing to interpolate towards, this is a pure instantaneous step, from the initial factor to the single listed one, exactly at that date:

Date

Factor

Before, and at, 15-Jul-2009

0.0

After 15-Jul-2009

1.0
