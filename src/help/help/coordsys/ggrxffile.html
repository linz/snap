GGRXF (GRIDDED GEODETIC RAGGED DATA EXCHANGE FORMAT) FOR DEFORMATION MODELS

This describes GGRXF, a new deformation-model file format that extends GGXF (Gridded Geodetic data eXchange Format) - the community standard this format targets - to let a single grid carry an independent time-series per node. Everywhere that new capability doesn't force a departure, this format adopts GGXF's own schema and conventions directly, to keep the gap between the two as narrow as possible. See "Why GGXF was investigated" and "Where this format departs from GGXF, and why" below. This document also includes a byte-level specification precise enough to implement an independent reader or writer from scratch. (Terminology requiring additional documentation is explained in more detail at the end of this document.)

Requirements

What this format has to actually support, independent of how any given requirement ends up being met: everything the existing New Zealand Geodetic Datum 2000 deformation model can represent, functionally, must remain representable -- not necessarily via the same attributes or schema -- while maintaining and/or adding:

  1. Per-node independent timing, not just per-node magnitude -- an existing region-wide spatial-function-times-time-function model can already give each node its own magnitude and direction of response (scaled from a shared time function by that node's own spatial coefficient), but every node is still forced onto the exact same segment schedule -- the same dates at which the rate of change shifts. Each grid node needs its own independently timed segments, not just its own independently scaled response to one shared schedule.
  2. Efficient query evaluation -- O(1)-ish lookup at any (longitude, latitude, date); no walking or summing a node's full history per query.
  3. Compact per-record storage -- each segment record itself stays lean, with no redundant fields, independent of how many nodes or segments the file as a whole holds.
  4. Sufficient range and precision together -- large one-time jumps (coseismic steps, many metres) and small compounding rates (mm/year over decades) both need to be representable without the accumulated error, or the storage ceiling, blowing out.
  5. Genuinely perpetual/secular motion -- a layer whose contribution extrapolates forever (matching what the existing model calls a velocity component's behaviour), optionally bounded only at the start.
  6. Deliberate, non-default early termination -- a segment can be authored to expect its motion to subside by a specific date, without that being the default assumption.
  7. Temporal supersession -- one layer replacing another over a specific footprint from a specific date (e.g. survey data superseding InSAR where InSAR itself has no valid measurement).
  8. Cross-layer summation -- independent physical contributions (the secular model, each distinct earthquake event, each InSAR patch) summed together.
  9. Spatially variable resolution -- both avoiding one wasteful nationwide bounding rectangle over sparse/irregular coverage, and representing the same event/time-window at multiple resolutions in one sub-region (a real example: the existing Secretary Island earthquake patch has three nested resolution tiers). The old format already solved this (nested containment + priority).
  10. Self-describing container with existing tooling, rather than hand-rolling cross-platform struct portability, compression, and inspection tools from scratch.
  11. Append-only extensibility -- new layers/patches addable over time without rewriting or republishing already-existing ones.

Why GGXF was investigated

The core problem this format exists to solve: every existing deformation-model format checked -- the LINZDEF binary format SNAP currently uses internally, PROJ (a widely used open-source coordinate-transformation software library)'s defmodel operation, and GGXF's own current specification -- decomposes deformation as a spatial grid of values multiplied by one time function shared across the entire grid. That forces any node-by-node variation in when something happened (not just how much) to be represented by resampling every node onto a synchronised, region-wide set of time slices, which can make the stored model many times larger than the original data. GGXF (descended from a 2018 LINZ proposal, OSGeo/PROJ#1001) is the most complete, currently-active standardisation effort in this space, so it was the natural place to check whether this problem was already solved.

It wasn't. In the GGXF specification text, and in the GGXF specification's own example encoding of LINZ's published NZGD2000 deformation model data (not a LINZ-produced or LINZ-maintained file -- compiled by GGXF's own project tooling from LINZ's underlying published dataset), every GGXF group's time function applies to every node in that group's grid uniformly, not per node. Real per-node time-varying data, such as that derived from InSAR analysis, has no representation in GGXF's current specification.

What this format adopts from GGXF

  • netCDF-4 (network Common Data Form, version 4) as the container. GGXF's own files use netCDF-4 group nesting (an HDF5 (Hierarchical Data Format, version 5) "enhanced data model" feature unavailable in older, "classic" netCDF). That same underlying technology natively supports compound types and CF (Climate and Forecast) ragged array representation, both of which this format's own per-node segment storage needs, independent of anything else GGXF does. netCDF-4 also offers a native VLEN (variable-length) type as an alternative way to store this same kind of ragged data, considered and rejected: VLEN elements are stored as separately heap-allocated blobs rather than one contiguous array, which generally compresses and chunks worse than CF's ragged array representation, and the offset/count bookkeeping CF's approach requires is something this format's own per-node CSR storage (below) needed to implement either way.
  • Cross-component summation. The GGXF specification's own example encoding of LINZ's NZGD2000 dataset (its ggxfGroups -- one for the secular/plate-motion model, one per historical earthquake patch) sums independent components at query time. The same architectural pattern is independently corroborated by PROJ's own defmodel operation, evaluated against a defmodel/GTG (Geodetic TIFF Grids) rendition of the same underlying dataset published on PROJ's own grid distribution server -- neither of these two files is LINZ's own authoritative model data (that is the CSV dataset LINZ publishes directly, nzgd2000-deformation-model on GitHub, also distributed as the nzgd2000_deformation_20180701_full.zip download -- the LINZDEF .bin format itself is a further compilation of that same CSV data for SNAP's own internal use, not the authoritative source, and is the artifact this new format is designed to replace); both are separately-produced implementations of that same published CSV dataset, converted into GGXF's and PROJ's own respective formats (PROJ does not consume GGXF itself; see "Where this format departs from GGXF" below). This format keeps that same summation architecture unchanged: independent layers -- distinct physical contributions, such as the secular model and each separate earthquake patch -- are always summed. This does not apply within a single layer where multiple grids describe the same time window at different resolutions (the next bullet below) -- there, exactly one grid is used, never summed with the others.
  • Containment + priority precedence (GGXF's childGrids/gridPriority mechanism: a more deeply nested grid always takes priority over its parent; descendant siblings that spatially overlap require an explicit, unique priority value -- root siblings are a departure from GGXF here, see "Where this format departs from GGXF, and why" below) is adopted directly as the solution to multiple grids describing the same time window at different spatial resolutions (a real example already exists in the current production model: the Secretary Island earthquake patch has three nested resolution tiers). See "Layers and grids" and "Grid resolution within a layer" below.
  • Affine-grid spatial indexing: coordinates computed from a linear transform plus integer row/ column indices (GGXF's affineCoeffs/iNodeCount/jNodeCount), rather than storing every node's own latitude/longitude explicitly. Used for both this format's ordinary scalar grids and its new per-node ragged grids. This also carries over GGXF's support for non-axis-aligned (rotated/sheared) grids, even though no grid produced so far needs it.
  • Named time function shapes and their composition semantics (GGXF's own functionType vocabulary -- linear/step/ramp/exponential/logBaseE/logBase10/quadratic/cyclic/ hyperbolicTangent, as implemented in GGXF's reference implementation, see "GGXF time function shapes" below). "Scalar with time function" grids adopt GGXF's own timeFunctions mechanism -- a summed list of these named shapes (each evaluated as its own refFunc(Δ) formula, unchanged from GGXF's own) scaling one shared per-grid spatial value, exactly as GGXF's own files do (its published NZGD2000 example sums two ramp entries for the real Dusky Sound earthquake patch) -- with one exception: what unit Δ itself is measured in departs from GGXF's own convention, for both grid types, see "Where this format departs from GGXF, and why" below. "Ragged segments" adopts the same composition semantics, not just the vocabulary: each segment's own segment_start_value is exactly the sum of every earlier segment's own now-frozen contribution (GGXF's endEpoch-clamp behaviour), cached once when the record is written rather than summed live at every query (see "Per-node ragged segment storage" below) -- what this format departs from GGXF on here is the storage mechanism this caching enables, not the underlying composition rule, see "Where this format departs from GGXF, and why" below.

Where this format departs from GGXF, and why

  • Per-node time series needs a different storage mechanism from GGXF's own, though the underlying composition rule is the same. GGXF's own timeFunctions record schema is adopted even for "ragged segments" (see "GGXF time function shapes" below) -- each segment declares its own named shape, exactly as GGXF's own function types do -- and the values produced are mathematically equivalent to GGXF's own summation (see "What this format adopts from GGXF" above): each earlier segment's own contribution, frozen after its own end exactly as GGXF's endEpoch clamp already behaves, sums to the constant segment_start_value carries. What GGXF's own mechanism cannot do is what makes a separate storage mechanism necessary here: CompoundTimeFunction sums every listed function on every query (as in GGXF's reference implementation) from an explicit list that must retain every historical contribution to keep producing the right sum -- correct where the physical contributions are genuinely few and permanent (secular + coseismic + postseismic), but as a node accumulates real breakpoints (up to 252 in the worst case, see "Numeric ranges"), that list would grow without bound, violating both requirement 2 (summing a growing list per query) and requirement 3 (an ever-growing per-node record). "Ragged segments" (below) avoids both by caching the sum of every completed contribution as segment_start_value and discarding the explicit list, storing and evaluating only the currently active segment -- while still using GGXF's own named-shape vocabulary for what that segment itself is.
  • Grid priority is not compared among a layer's own root grids -- real GGXF requires exactly that. Real GGXF's own spec is unambiguous: "all intersecting root grids must be given a unique gridPriority value... gridPriority values must be unique amongst intersecting sibling grids within one family," with no root/non-root distinction in that requirement. This format instead resolves a layer's own root grids by plain first-match in file order, reserving gridPriority entirely for grids nested under a nest root (see "Layers and grids" and "Grid resolution within a layer" above) -- a deliberate narrowing, not an oversight. The motivation is downstream: a reader with stricter performance/complexity constraints needs to reproduce this format's own resolution behaviour exactly, and requiring real numeric priority comparison at the root level would force such a reader to do genuine tie-breaking work at that level. Any set of genuinely overlapping root-tier grids can instead be written as one nest root plus flattened children (see "Layers and grids" above), so nothing this format needs to express is lost by this narrowing.
  • This format does not target compliance with GGXF's own specification, and that was a deliberate choice, not an oversight. Early in this design process there was a pull toward favouring whatever the existing PROJ/GGXF tooling ecosystem could already read. This was reconsidered: an authoritative format's correctness doesn't depend on what any particular downstream tool currently implements. LINZ already runs exactly this pattern for the existing deformation model: the authoritative source is the CSV dataset LINZ publishes directly (nzgd2000-deformation-model on GitHub, also distributed as the nzgd2000_deformation_20180701_full.zip download); LINZ itself compiles that CSV data into the LINZDEF .bin format for the SNAP software to read directly -- the very artifact this new format is designed to replace; separate JSON+GeoTIFF files published to PROJ's own grid server are yet another distinct export, for a different consumer, and PROJ does not read LINZDEF either. The same pattern applies here: if GGXF or PROJ compatibility is ever wanted for this new format, that is a separate export/ conversion step, not a constraint on this format's own design.
  • PROJ itself does not read GGXF files today, so targeting GGXF compliance would not even buy real interoperability with PROJ specifically. From the public GitHub discussion that led to GGXF's creation (OSGeo/PROJ#1001, 38 comments, 2018-2020): PROJ's own maintainers deliberately decided to keep a heavy, HDF5-based format out of PROJ's own codebase rather than build it in -- one maintainer (Even Rouault) wrote "we don't want proj to depend on libtiff and libgeotiff"; the original proposer (Chris Crook, from LINZ) wrote "Like HDF5 a complete implementation would be heavy lifting for proj"; another maintainer (Kristian Evers) wrote "PROJ will only be a consumer of the files" -- meaning GGXF was intentionally built as an independent standard specifically so PROJ wouldn't have to absorb its implementation cost. More than four years after that discussion, PROJ's actual dependency list is still just SQLite3 (required) and two optional libraries (libtiff, libcurl) -- no netCDF, no HDF5. PROJ's own, currently-deployed New Zealand deformation model (distributed from PROJ's own grid distribution server) is plain JSON plus GTG grid files, not GGXF.
  • GeoTIFF (the format PROJ actually uses in practice) cannot represent this format's core need regardless of any of the above. A GeoTIFF image requires every pixel to have the same fixed-size data layout; there is no way to store a different number of records per pixel within one image. Representing this format's variable-length-per-node segment lists in GeoTIFF would require padding every node to a fixed maximum size (wasteful for the many nodes with far fewer segments than the maximum) or hiding an unstructured blob inside a private, non-standard image tag, which is not meaningful format support.
  • This format's "terminal node" mechanism assumes a final segment continues indefinitely by default, unless it has an explicit end date or is superseded by another layer (see "Terminal-node evaluation" below). For scalar_with_time_function, own_end_date is an extension of GGXF's own native per-entry endDate clamp (see "GGXF time function shapes" above), generalised from one timeFunctions entry to a whole grid: clamping the query date at the grid level, before summing, is mathematically identical to setting that same endDate on every entry, for 8 of the 9 shapes -- only ramp, whose own endDate is load-bearing to its own shape rather than a pure external clamp, cannot be represented that way, which is why the grid-level form is needed rather than relying on native per-entry endDate directly. For ragged_segments, own_end_day has no GGXF equivalent at all -- that grid type has no timeFunctions to extend from. Temporal supersession (requirement 7) is the temporal analogue of the containment + priority mechanism this format already adopts from GGXF for spatial resolution (gridPriority, see "Grid resolution within a layer" above). That mechanism is spatial-only and time-blind (see above); temporal supersession applies the same kind of override along the time axis instead, evaluated per query against has_end_day/own_end_date/ own_end_day -- not a reuse of GGXF's own priority resolution.
  • Δ (the input to every refFunc shape) is measured in days, not GGXF's own years. GGXF's own convention (DateToEpoch) expresses every epoch as a calendar-exact decimal year; this format instead uses the real day-count difference between the two dates involved directly, with no year-length conversion anywhere in a reader's own evaluation path, for either grid type. Two reasons together: it gives this format exactly one Δ-evaluation rule, not two -- ragged_segments already needed compact day counts for its own storage (see the first bullet above), so extending that to scalar_with_time_function as well removes the only place a second, different rule would otherwise be needed; and a real day count needs no year-length convention chosen at all, whereas any years-denominated Δ does, and different reasonable choices of "what is a year" genuinely disagree with each other. For example: a Δ spanning exactly one calendar year that happens to be a leap year (366 real days) is 1.0 under GGXF's own year-anchored convention (a whole calendar year always contributes exactly 1.0 to the epoch, by construction) but 366/365.2425 ≈ 1.0021 under a real day count divided by a fixed year length such as 365.2425 -- both are internally consistent and well-defined, neither is wrong, they simply disagree, and days sidesteps needing to pick one of them inside the format's own reader at all. This only actually changes linear's own scaleFactor unit (days-denominated here, not years-denominated as in GGXF's own convention) -- every other shape's refFunc(Δ) is a ratio or bounded value, not Δ directly, so its own scaleFactor stays a dimensionless amplitude regardless of what unit Δ itself is measured in.

Format specification

Data type names used throughout this specification (int32, uint16, float64, ...) always specify an exact, fixed byte width -- int32 is a 4-byte signed integer, uint16 a 2-byte unsigned integer, and so on, matching the C99 stdint.h/IEEE-754 naming convention.

Byte order (endianness) needs no decision anywhere in this specification. Every value stored in an HDF5 file carries its own byte-order tag as part of the file's own type metadata, set by whichever library wrote it; any compliant netCDF-4/HDF5 library reads that tag and converts to the host's own native order automatically on read. A from-scratch reader only needs to correctly implement (or link against) real HDF5 type-descriptor handling.

A displacement component suffix, _e/_n[/_u] (East/North[/Up]), appears on several field names below where a grid stores 2 or 3 independent components rather than one. Written as _{enu} wherever a statement applies independently and identically to each of _e/_n/_u (braces, not brackets, so as not to be confused with actual array indexing).

Container

One netCDF-4 file (HDF5-based; write and read via a real netCDF-4 library, e.g. Python's netCDF4 package, not a raw HDF5 library directly -- this avoids having to separately re-implement netCDF-4's own internal HDF5 conventions).

Conventions is netCDF's own standard root attribute identifying which conventions a file follows. This format's own value is "GGRXF-1.0", not "GGXF-1.0": ragged_segments groups (see "Per-node ragged segment storage" below) don't validate against GGXF's own group-attribute requirements, and a GGXF-compliant reader treats that as a whole-file load failure, not a per-group skip -- claiming Conventions="GGXF-1.0" would therefore misrepresent any file that uses ragged_segments at all. "GGRXF-1.0" names this format's own relationship to GGXF directly (GGXF plus the ragged_segments extension) while staying honestly distinct from it, and is structured so it can become a real GGXF-x.y value later if every grid type this format defines is ever brought to full conformance.

content is "deformationModel", GGXF's own predefined content-type keyword (GGXF_CONTENT_DEFORMATION_MODEL in GGXF's own reference implementation), matching this file's actual content exactly -- no departure from GGXF here. GGXF ties two further requirements to this specific content type: which parameter names a ggxfGroup may declare (see "Parameters" below), and that timeFunctions is a per-layer, not per-grid, attribute (see "Layer attributes" below) -- already reflected in this format's own schema.

parameters is documented in full in "Parameters" below.

Parameters

netCDF/HDF5 attributes can't hold nested structures directly, so parameters (a real array of records, same mechanism as timeFunctions -- see "Time functions" above) is stored the same way: every element, and every field of every element, is its own separate, flat, dot-named attribute. All names below are written relative to parameters itself -- e.g. count is really the attribute parameters.count on disk, <n>.parameterName is really parameters.<n>.parameterName, and so on:

Name Kind dtype Shape Required Meaning
count attribute uint8 scalar required number of parameters, n in 0..count-1 below
<n>.parameterName attribute string scalar required, one per parameter one of GGXF's own conventional keyword names for the content type (Table B.4)
<n>.parameterSet attribute string scalar optional, one per parameter; defaults to that parameter's own parameterName if absent parameters sharing one parameterSet value combine into a single netCDF vector variable (GGXF §6.3.5.1)
<n>.unitName attribute string scalar required, one per parameter the real-valued unit this parameter's own values are expressed in
<n>.unitSiRatio attribute float64 scalar optional, one per parameter; defaults to 1.0 (SI) if absent multiplier converting unitName to the SI unit
<n>.noDataFlag attribute float64 scalar optional, one per parameter the value, in this parameter's own units, that signifies no data

noDataFlag is GGXF's own per-parameter no-data declaration, but in real units, for non-netCDF encodings (YAML/CSV) that have no separate attribute mechanism of their own for this -- it is never read anywhere in GGXF's own reference netCDF reader/writer. This format still declares it, real GGXF field and all, but has nothing meaningful in real (millimetre) units to put there, so it reuses 2147483647 (int32's own maximum value) rather than inventing a separate, dimensionally meaningless "real" number for a field nothing in this format's own netCDF path actually reads.

Three names here are easy to conflate, but they answer only two distinct questions, not three:

  1. "Does this layer carry this parameter at all?" -- gridParameters (see "Layer attributes" below) alone: an omitted parameter has no storage anywhere in that layer, so it contributes zero uniformly, not as a per-node decision.
  2. "Does this specific node's own value, within a parameter the layer does carry, mean no data?" -- noDataFlag and missing_value (see "Per-grid time function storage" below) both answer this same, narrower, per-node question -- two different encodings of the same sentinel for two different serialisations, not two different questions: noDataFlag, in a parameter's own units, for YAML/CSV (unused by this format's own netCDF path); missing_value, as the packed raw integer, for netCDF/CF (what a reader of this format actually checks).

The three parameters of a deformation model (content = "deformationModel", see "Container" above): displacementEast/displacementNorth/displacementUp (GGXF's own conventional keyword names), all sharing parameterSet = "displacement" so they combine into one netCDF vector variable, unitName = "millimetre" and unitSiRatio = 0.001 for all three (this format's own existing millimetre-scale storage, see "Numeric ranges" below), and noDataFlag = 2147483647 for all three, per the previous paragraph.

sourceCrsWkt/targetCrsWkt/interpolationCrsWkt are GGXF's own root attributes (GGXF_ATTR_SOURCE_CRS_WKT/GGXF_ATTR_TARGET_CRS_WKT/GGXF_ATTR_INTERPOLATION_CRS_WKT in the reference implementation) -- real OGC WKT text, not an EPSG-code shorthand, e.g. for NZGD2000 (EPSG:4167, as returned by pyproj.CRS.from_epsg(4167).to_wkt()): GEOGCRS["NZGD2000",DATUM["New Zealand Geodetic Datum 2000",...],...,AXIS["geodetic latitude (Lat)",north,ORDER[1]],AXIS["geodetic longitude (Lon)",east,ORDER[2]],...] (see "Grid spatial indexing attributes" below for what that axis order means for affineCoeffs).

Only interpolationCrsWkt is mandatory in GGXF's own schema; sourceCrsWkt/targetCrsWkt are optional. interpolationCrsWkt is real GGXF intent, read at query time in the reference implementation's own CSV/YAML tooling (GGXF.nodeCoordinateParametersFromCrsWkt), but is not actually parsed by the netCDF Grid class for affineCoeffs itself. sourceCrsWkt/ targetCrsWkt are consulted by nothing at all in the reference implementation -- neither appears anywhere in GGXF.py/NetCDF.py (in the scripts/GGXF/ directory of the opengeospatial/CRS-Gridded-Geodetic-data-eXchange-Format repository) beyond generic string-type validation.

operationAccuracy is GGXF's own optional root attribute (Recommendation 14, GGXF_ATTR_OPERATION_ACCURACY in the reference implementation, a plain float with no further structure) -- like sourceCrsWkt/targetCrsWkt, consulted by nothing in query evaluation, documentation only. The accuracy this format is designed for is stated elsewhere in this document (see "Numeric ranges" below, about 10mm/0.01m); a writer targeting that would set operationAccuracy = 0.01.

modelVersion is this format's own addition, not part of GGXF's own root-attribute schema -- distinct from Conventions, which identifies this format's own version ("GGRXF-1.0"), not the source model's. A producer-defined string with no format-mandated structure -- deliberately not constrained to a date, unlike the currently-published LINZDEF model's own version (always a YYYYMMDD release-date string, baked directly into its compiled binary's own header) -- so a GGRXF file built from a source with its own existing versioning scheme (a semantic-version string such as 1.15.10, for instance) can use it as-is, without this format imposing a different one.

Layers and grids

Each independent physical contribution (the secular/plate-motion model, each distinct historical earthquake patch, each InSAR-fit region) is one netCDF-4 group, a layer. A layer group is a pure container: it carries no data of its own. A scalar_with_time_function layer's own grids are netCDF-4 grid subgroups nested directly inside it -- uniformly, even where a layer needs only a single grid, so there is exactly one on-disk shape to reason about for that grid type, not a flat single-grid case and a separate nested-grid case. A ragged_segments layer's own grids are stored differently -- as layer-wide arrays indexed by a grid dimension, not subgroups at all -- see "Consolidated storage for ragged_segments grids" below. grid_type (below) determines which of the two shapes a given layer uses; every grid within one layer shares it (see "Grid type" below).

A new layer supersedes at most one existing layer -- nothing in this format's own requirements needs one layer replacing several at once.

This id-lookup step assumes the superseded layer is already published in a file being opened, mutated, and written back to -- the ordinary append-only case (requirement 11) of adding a superseding layer to an existing file over time. Constructing an entire file in one go, where both an original layer and a layer meant to supersede it are already known before any file exists at all, does not need supersedes in the first place: author the original layer's own has_end_day and its own own_end_date/own_end_day directly at creation instead of superseding it after the fact. If the supersedes provenance attribute is still wanted even then, build the file in two separate steps -- publish the original layer first, run the layer-listing tool to discover its own id, then add the superseding layer afterwards referencing that id -- rather than inventing an id for a layer that doesn't exist on disk yet.

Scoped per layer, not per file, so different layers -- including ones appended later, covering entirely different time windows -- can each choose whichever reference date suits their own data, independent of every other layer already in the file (matching requirement 11, append-only extensibility). scalar_with_time_function grids have no use for it at all: own_end_date and a layer's own timeFunctions (see "Time functions" below) are self-contained ISO-8601 dates, compared directly against the query's own date, with no day-count conversion anywhere in that path -- a layer containing only such grids simply omits reference_date. reference_date has no relationship to interpolationCrsWkt -- it is an arbitrary, per-layer storage detail chosen purely to keep reference_day/day_delta/own_end_day small, not a geodetic reference epoch, and it is never required to match, or even be near, the CRS's own datum reference epoch.

timeFunctions: documented in full in "Time functions" below.

Time functions

matches real GGXF exactly -- timeFunctions is a per-ggxfGroup (layer) attribute in GGXF's own schema for content = "deformationModel", not a per-grid one (see the ContentTypes table in GGXF's reference implementation, GGXF_Types.py), so every scalar_with_time_function grid nested in one layer (e.g. childGrids for spatial resolution, see "Grid resolution within a layer" below) shares this one summed definition -- the physical phenomenon one layer represents has a single time-behaviour regardless of which resolution grid a query point resolves to; only the spatial values (displacement) differ by grid. A layer containing only ragged_segments grid(s) omits timeFunctions entirely -- that grid type has its own, unrelated per-segment function_type_{enu} mechanism (see "Per-node ragged segment storage" below) and never reads a layer's timeFunctions.

netCDF/HDF5 attributes can't hold nested structures directly, so timeFunctions (a real array of records) is stored the same way GGXF's own files store any array-valued attribute: every element, and every field of every element, is its own separate, flat, dot-named attribute -- matching GGXF's own reference reader exactly (any X.count-suffixed key marks X as an array; this isn't specific to timeFunctions). Each of the count entries is independently a full record -- different entries can be different shapes (the real Dusky Sound example is two summed ramp entries, but nothing requires entries to share a shape). All names below are written relative to timeFunctions itself -- e.g. count is really the attribute timeFunctions.count on disk, <n>.functionType is really timeFunctions.<n>.functionType, and so on:

The table above describes a scalar_with_time_function grid, which stores these fields exactly as shown -- attributes on that grid's own netCDF-4 subgroup. A ragged_segments grid stores the same fields, with the same meanings, differently -- see "Consolidated storage for ragged_segments grids" below. Every formula in the rest of this section applies identically to both; only where the fields are addressed from differs.

Together, iNodeCount and jNodeCount give one grid's own total node count, N = iNodeCount * jNodeCount -- used throughout the rest of this section (both grid types) for the containment/ corner-weight formulas below, and for a scalar_with_time_function grid's own per-node displacement array ("Per-grid time function storage" below). A ragged_segments grid's own per-node arrays use a separately-scoped, layer-wide N instead -- see "Per-node ragged segment storage" below, which redefines N for that grid type specifically before using it.

Both grid types use the same affine-grid spatial indexing: each grid has its own affineCoeffs, iNodeCount, and jNodeCount. GGXF's own reference implementation types iNodeCount/ jNodeCount (and gridPriority) as plain Python int with no declared width, so there's no fixed-width precedent to borrow from GGXF; uint32's maximum of 4,294,967,295 nodes per dimension is this format's own choice, well beyond any real or plausible future grid. No separate per-node coordinate storage -- node (i, j)'s coordinates are computed as

c0 = affineCoeffs[0] + affineCoeffs[1]*i + affineCoeffs[2]*j
c1 = affineCoeffs[3] + affineCoeffs[4]*i + affineCoeffs[5]*j

c0/c1 are generic here deliberately: GGXF's own schema only says "6 floats" -- it does not say which is longitude and which is latitude, since that identity is a per-file fact read from that file's own interpolationCrsWkt (see "Container" above), specifically its own AXIS[...] clauses in the order they appear -- this is real GGXF intent (GGXF.nodeCoordinateParametersFromCrsWkt), adopted here throughout: a reader determines c0's and c1's own identity from interpolationCrsWkt, not from a fixed rule in this schema. The interpolationCrsWkt used for NZGD2000 (EPSG:4167) declares AXIS["geodetic latitude (Lat)",north,ORDER[1]] before AXIS["geodetic longitude (Lon)",east,ORDER[2]], so in files that use it, c0 is latitude and c1 is longitude -- a consequence of reading that CRS, not a separate rule this format states independently of it. (The netCDF Grid class in GGXF's own reference implementation never actually performs this read for affineCoeffs itself -- only its separate CSV/YAML grid-import tooling calls nodeCoordinateParametersFromCrsWkt -- but the intent, that column identity follows the CRS, is what this format adopts; this document's own separate convention for writing a query point in prose, (longitude, latitude, date), is unrelated and unchanged by any of this.) This matches GGXF's own reference implementation (GGXF.py in the opengeospatial/CRS-Gridded-Geodetic-data-eXchange-Format repository: affineCoeffs reshaped to a 2x3 array, xy = xy0 + tfm.dot([i, j])).

The inverse -- (c0, c1) to fractional node index (i, j), needed by "Grid resolution within a layer" below (the containment check) and "Query evaluation, end to end" below (finding the 4 corner nodes and their bilinear weights) -- inverts the 2x2 linear part of the same transform:

det = affineCoeffs[1]*affineCoeffs[5] - affineCoeffs[2]*affineCoeffs[4]
i = (affineCoeffs[5]*(c0 - affineCoeffs[0]) - affineCoeffs[2]*(c1 - affineCoeffs[3])) / det
j = (affineCoeffs[1]*(c1 - affineCoeffs[3]) - affineCoeffs[4]*(c0 - affineCoeffs[0])) / det

GGXF.py's own reference implementation computes the same inverse: ij = inv(tfm).dot(xy - xy0).

The containment check itself, given the fractional (i, j) above, is

TOLERANCE_RATIO = 0.00001  # same value as GGXF's own TOLERANCE_RATIO (GGXF.py)
contained = (-TOLERANCE_RATIO <= i <= iNodeCount - 1 + TOLERANCE_RATIO) and (-TOLERANCE_RATIO <= j <= jNodeCount - 1 + TOLERANCE_RATIO)

-- iNodeCount - 1/jNodeCount - 1, not iNodeCount/jNodeCount, since those attributes are node counts and valid indices run 0 to count - 1. The TOLERANCE_RATIO term is required, not cosmetic: two independently-computed affine-inverse results for the same real-world point on a shared grid boundary aren't guaranteed to land on exactly 0 or iNodeCount - 1 in floating point, so a strict equality check can wrongly exclude a point that genuinely lies on the boundary. GGXF's own reference implementation guards against exactly this with a per-grid tolerance derived from one grid step's own real-world length (self._tolerance = norm(calcxy([0,1]) - calcxy([1,0])) * TOLERANCE_RATIO in GGXF.py); this format applies the same TOLERANCE_RATIO value directly in index units instead of converting through interpolationCrsWkt-space and back, since one grid-index unit is already exactly one grid cell.

The base corner used by both the containment check and bilinear interpolation is (bi, bj) = (min(iNodeCount - 2, floor(i)), min(jNodeCount - 2, floor(j))), not (floor(i), floor(j)) directly -- a query point exactly on the grid's own last row/column of nodes (a valid, contained boundary point, per the closed containment check above) would otherwise put the opposite corner one node past the last valid index. This requires iNodeCount/jNodeCount >= 2, the same minimum GGXF's own reference implementation already enforces. The 4 corners are then (bi, bj), (bi+1, bj), (bi, bj+1), and (bi+1, bj+1), with bilinear weights taken from the fractional parts (i - bi, j - bj) -- at the clamped boundary these correctly evaluate to 1.0 on the last node and 0.0 on the other, not an out-of-bounds read. GGXF's own Grid.cellij() (GGXF.py) applies the same clamp: cellmax = [iNodeCount - 2, jNodeCount - 2], cij = max([0, 0], min(cellmax, floor(rij))).

This 4-corner procedure is specific to interpolationMethod = "bilinear". A layer declaring bicubic or biquadratic instead needs a wider surrounding node neighbourhood than these same 4 corners reweighted -- this document doesn't specify that neighbourhood-selection procedure; see GGXF's own reference implementation (GGXF.py) directly.

For a "ragged segments" grid, node (i, j) maps to a single integer node_index = i * jNodeCount + j, used to index into the per-node arrays below.

A grid may itself have further grids nested inside it -- child grids, describing the same physical contribution at finer spatial resolution over some or all of the parent's own footprint (the real Secretary Island earthquake patch is exactly this: three tiers, each about 4x finer than the last, all sharing one step contribution at one event date). How a child grid is attached to its own parent differs by grid_type (see "Grid type" above): a scalar_with_time_function grid nests its own child grids as further netCDF-4 subgroups (child_grids below refers to this subgroup nesting); a ragged_segments grid instead points each child at its own parent via parent_grid_index -- see "Consolidated storage for ragged_segments grids" below. Both express the identical concept and resolve identically (see "Grid resolution within a layer" below); only the on-disk mechanism differs.

A layer's own root grids -- for a scalar_with_time_function grid, the grid subgroups directly inside the layer group; for a ragged_segments grid, every grid whose own parent_grid_index is the root sentinel (see "Consolidated storage for ragged_segments grids" below) -- are resolved by plain first-match in file order. "File order" is a concrete, on-disk fact, not whatever order a given HDF5/netCDF-4 library's own group-iteration API happens to return (which is not guaranteed to reflect write order): for a scalar_with_time_function grid, each root grid's own netCDF-4 group is named grid_<N>, and file order is ascending numeric order by N -- recoverable directly from each group's own name by any reader, independent of HDF5 iteration order, library, or version. For a ragged_segments grid, file order is simply ascending order along the grid dimension's own index -- a plain array position assigned at write time, with no group-iteration-order ambiguity to guard against in the first place. Either way, how a reader actually uses that order to resolve a query point -- an early-exit linear scan, a precomputed sort, a spatial index, or anything else -- is an implementation detail this format doesn't constrain. gridPriority is never read or compared among root siblings, full stop, even where two root grids' extents genuinely overlap (see "Grid resolution within a layer" below). Each root grid is either a plain grid with no child grids -- which must carry no gridPriority at all -- or a nest root: a grid with one or more child grids, which must carry gridPriority exactly 0.

A nest root's entire descendant subtree -- however many levels deep a producer actually nests it -- must, flattened across every depth, carry gridPriority values forming exactly the consecutive set {1, ..., n-1} for n-1 total descendants: no gaps, no duplicates, and every descendant requires a real, distinct value, including same-resolution siblings that merely touch along a shared edge or corner (adjacent same-resolution tiles of one adaptively-tiled region are required to carry identical node values along a shared edge, so any of them gives the identical bilinear-interpolation answer there regardless of which one a query resolves to -- but the value is still required, purely to keep the flattened set gapless and unambiguous). How many levels deep a producer chooses to nest that subtree is a writer-side implementation detail: from a reader's perspective, one nest root plus its flat, priority-ordered descendant list is the whole shape, and nothing needs to preserve deeper nesting once flattened. uint8 is ample: gridPriority's flattened set only ever spans one nest root's own descendant subtree, never a global ordering across the whole file, and getting anywhere near 255 descendants under one nest root would call for restructuring into a separate layer, not a wider field.

See "Grid resolution within a layer" below for how a query point resolves through this structure.

Consolidated storage for ragged_segments grids

A ragged_segments grid's own affineCoeffs/iNodeCount/jNodeCount/gridPriority -- and the new parent_grid_index field that expresses child-grid nesting for this grid type (see above) -- are stored as layer-wide variables indexed by a grid dimension (length = the total grid count in this layer, at every nesting depth: there is no separate storage concept for nesting depth, only a derived relationship via parent_grid_index), rather than as attributes of one grid's own netCDF-4 subgroup the way a scalar_with_time_function grid stores them:

Name Kind dtype Shape Required Meaning
affineCoeffs variable float64 (grid, 6) required as the table above, one row per grid
iNodeCount variable uint32 (grid,) required as the table above, one entry per grid
jNodeCount variable uint32 (grid,) required as the table above, one entry per grid
gridPriority variable uint8 (grid,) same requirement as the table above (forbidden on a childless root, required exactly 0 on a nest root, required forming the flattened 1..n-1 set on a nest root's own descendants) -- meaningless and unread for a root grid, stored anyway rather than making this a sparse/optional array as the table above, one entry per grid

0 doesn't work as parent_grid_index's own root sentinel: grid index 0 is an ordinary, valid array position like any other, and if it happens to be a nest root, its own children need to store parent_grid_index = 0 to point at it -- reusing 0 to also mean "no parent" would make a childless root at index 0 indistinguishable from a nest root's own child, silently misresolving. A sentinel must be a value no real grid index can ever take; uint32's own max value does that while keeping this field unsigned like iNodeCount/jNodeCount above -- the same idiom this format already uses for "none" elsewhere (missing_value/noDataFlag = 2147483647, int32's own max, see "Parameters" above) -- rather than introducing this format's first signed index field.

A reader builds one small in-memory index at file-open time -- parent grid index to the list of that parent's own child grid indices, O(grid count), built once -- instead of relying on netCDF group nesting to express parent/child relationships; see "Grid resolution within a layer" below for how resolution walks this index.

node_index (i * jNodeCount + j, above) is local to one grid's own node range; see grid_node_offset in "Per-node ragged segment storage" below for how a ragged_segments grid's own slice of the layer-wide node dimension is found.

Grid resolution within a layer

A layer with more than one grid resolves to exactly one grid at any given query point: at the root level by plain first-match (see "Layers and grids" above), then recursively preferring the most deeply nested grid that still covers the query point via containment + priority (adapted from GGXF's own childGrids/gridPriority mechanism, see "What this format adopts from GGXF" above), so every point ends up using the highest-resolution grid available there, never a coarser one where a finer one exists.

  1. Among the current set of sibling grids (a layer's own root grids, to start): at the root level, take the first one (in file order) whose extent -- computed from its own affineCoeffs/iNodeCount/jNodeCount, a pure containment check, no data read or interpolated yet -- contains the query point, without reading or comparing gridPriority at all, even where more than one root grid's extent contains the point. At every other level (resolving a nest root's own child grids, or a deeper descendant's own child grids -- child_grids subgroups for a scalar_with_time_function grid, parent_grid_index lookups for a ragged_segments grid, see "Grid spatial indexing attributes" above), find every sibling whose extent contains the query point; if more than one does, take the one with the highest gridPriority (every genuine descendant carries a distinct value, guaranteed by construction -- see "Layers and grids" above).
  2. If none do, this layer contributes exactly 0 at this point. This covers both a point outside every root grid's own extent, and a point falling in a genuine coverage gap between siblings -- a quadrant discarded as empty at build time is simply never written to the file, so a gap needs no explicit masking of its own.
  3. Take that grid's own child grids as the new "current set of sibling grids" and repeat from step
    1. Recursion stops -- using whichever grid was selected the last time step 1 found a match -- once no child grid covers the point, including immediately for a grid with no children at all.

The grid found this way is then evaluated exactly as described in "Query evaluation, end to end" below, according to its own grid_type. This resolution never depends on the query date -- which grid a point resolves to is fixed by location alone; terminal-node supersession (see "Terminal-node evaluation" below) is a separate, date-conditional check applied afterward, once a grid is already selected.

Grid type

grid_type (see "Layer attributes" above for its table entry) is "scalar_with_time_function" or "ragged_segments" -- unlike function_type_{enu} below (one value per segment, where a compact integer code is chosen instead, since there are many of them), there is no storage argument against a plain string here: one value per layer, not per grid or per segment.

It is a per-layer attribute specifically, not a per-grid one, and every grid in that layer's own grids, at every nesting depth, is required to match it -- a layer cannot mix the two grid types. The two types already need incompatible layer attributes (timeFunctions/gridParameters, required only for scalar_with_time_function, vs. reference_date, required only for ragged_segments -- see "Layer attributes" above), so a mixed layer could never satisfy both grid types' own requirements at once regardless; this format makes that structural rather than leaving it to an unenforced convention. A string rather than a boolean, still, leaving room for a future third grid type without changing the field's own type.

"ragged segments" is technically a strict superset of "scalar with time function" (nothing stops every node sharing one time series from instead holding its own duplicated, pre-scaled copy of it), but that would needlessly pay the storage cost of per-node independent timing (requirement 1) everywhere, including the many grids that never need it.

"scalar with time function" adopts GGXF's own timeFunctions/gridParameters mechanism directly (see "Per-grid time function storage" below), since every node in such a grid genuinely shares one time function -- exactly the case GGXF, the LINZDEF format, and PROJ's defmodel all already handle. "ragged segments" keeps this format's own storage mechanism instead -- not because its underlying composition semantics differ from GGXF's own summation (they don't, see "What this format adopts from GGXF" and "Where this format departs from GGXF, and why" above), but because GGXF's own mechanism would need to retain every historical contribution explicitly to keep summing them, growing without bound as a node accumulates real breakpoints; this format instead caches their combined effect once, per segment (see "Per-node ragged segment storage" below).

GGXF time function shapes

The nine functionType shapes below are GGXF's own named time functions, transcribed here (from GGXF's public reference implementation, opengeospatial/CRS-Gridded-Geodetic-data-eXchange-Format) for a byte-level reader's convenience. GGXF's own specification and reference implementation are the authoritative source for these formulas -- any divergence between this table's own refFunc(Δ) formulas and Requires columns and GGXF's own behaviour is an error in this document, not a deliberate departure, and should be corrected to match GGXF exactly, not the other way round. This authority applies to the shapes themselves only -- what unit Δ itself is measured in is a separate matter, and this format does deliberately depart from GGXF there, uniformly across every shape and both grid types (see "Where this format departs from GGXF, and why" above).

Every shape below is evaluated relative to its own required date parameter -- see the Requires column -- scaled by its own scaleFactor; written Δ below, meaning "the real day-count difference between the query date and that parameter's own date." Δ is always in days here -- not GGXF's own years, see "Where this format departs from GGXF, and why" above for why -- and this applies uniformly to all nine shapes below, not just linear. timeConstant (exponential/logBaseE/logBase10/hyperbolicTangent) and frequency (cyclic) are only ever combined with Δ by division or multiplication, so they are days-denominated here for the same reason, keeping every ratio unitless.

eventDate names the moment step/exponential/logBaseE/logBase10/hyperbolicTangent are each centred on -- their own required Δ = 0 point (a discrete jump for step, a decay/transition's own start for the other four).

functionReferenceDate is a separate, independently optional parameter on every shape, not only the three that require it below -- independent of whatever Requires lists (including eventDate where a shape has one), supplying it activates GGXF's own zeroing subtraction (refFunc(Δ) − refFunc(Δ_ref), where Δ_ref is Δ evaluated at functionReferenceDate itself, in place of refFunc(Δ) alone) -- it only ever affects where the output is pinned to zero, never where a shape's own transition happens, which stays fixed at its Requires date(s) regardless.

startDate is additionally optional on linear alone (see "Time functions" above), and must equal functionReferenceDate when present -- since Δ is already (query date) − functionReferenceDate, this makes (query date) < startDate and Δ < 0 the same condition, so linear's own row below states the delayed-onset case directly in terms of Δ, with no separate mechanism to define. Omitting startDate entirely keeps linear unbounded in both directions, reproducing the existing model's own velocity behaviour exactly (see "Per-grid time function storage" below).

A layer's own timeFunctions.<n>'s own reference/event dates (shared by every scalar_with_time_function grid nested within it) are stored as ISO-8601 date-time strings, the same real encoding GGXF itself uses (see "Layer attributes" above) -- but a reader computes Δ from them as the real day-count difference between the two dates involved (see "Query evaluation, end to end" below), not via GGXF's own DateToEpoch algorithm, per "Where this format departs from GGXF, and why" above.

ragged_segments is this format's own departure from GGXF in a second, independent respect (see "Segment record" and "Per-node ragged segment storage" below for why this storage mechanism exists at all): its own reference_day/day_delta are already stored as day counts, so computing Δ for a ragged segment needs no conversion at all here -- it is that stored day-count difference directly, with segment_scale_factor itself days-denominated for the same reason as linear above (see "Numeric ranges" below for its own scale).

The Code column is this format's own compact uint8 encoding, used only by function_type_{enu} ("Per-node ragged segment storage" below), where per-segment cardinality makes a string wasteful; a layer's own timeFunctions.<n>.functionType declares GGXF's own literal string value directly (see "Layer attributes" above), since that is a per-layer, not per-segment, attribute, and the cardinality argument for a compact code doesn't apply there.

Code functionType Requires refFunc(Δ) Shape
0 linear functionReferenceDate 0 if startDate is present and Δ < 0; Δ otherwise unbounded rate through zero, or delayed onset if startDate is present
1 step eventDate 1 if Δ ≥ 0 else 0 instantaneous jump
2 ramp startDate, endDate 0 if Δ < 0; Δ/Δ_end if 0 ≤ Δ < Δ_end; 1 if Δ ≥ Δ_end (Δ from startDate, Δ_end = endDate − startDate, both in days) bounded transition

An ordinary grid of scalar values (one per parameter this layer's own gridParameters declares -- see "Layer attributes" above), scaled by the sum of its own layer's timeFunctions entries evaluated at the query time (timeFunctions is declared once per layer, not per grid) -- adopting GGXF's own timeFunctions/CompoundTimeFunction mechanism directly (see "What this format adopts from GGXF" above). Covers every component that does not need per-node time variation (the secular/plate-motion grid, and any simple historical patch whose behaviour is uniform across its own footprint).

Every node's own magnitude/direction coefficients, across every parameter this layer's grids carry, are packed into one displacement vector variable -- GGXF's own convention (§6.3.5.1) for parameters sharing one parameterSet (see "Parameters" above: displacementEast, displacementNorth and displacementUp all share parameterSet = "displacement", hence the variable's own name). displacementCount (2 or 3, per this layer's own gridParameters) is GGXF's own dimension naming convention, f"{parameterSet}Count". Indexed the same way as every other per-node array for its own (i, j) dimensions (see "Grid spatial indexing attributes" below for the shared (i, j) -> node_index mapping); its own third dimension is which parameter, in this layer's own gridParameters order.

Each grid also carries its own scale_factor attribute -- GGXF's own standard netCDF packing convention (§6.3.5.4, as implemented by GGXF's reference writer, the Writer class in NetCDF.py, in its own variableAttributes method): the real-valued unit one raw displacement count represents for that specific grid, chosen at generation time to suit that grid's own value range and required precision; no add_offset is needed alongside it, since this format's own values are symmetric around zero. GGXF itself leaves packing optional, a per-file writer's choice: its own test data includes both a packed example (def_packed.cdl, int16 + scale_factor) and an unpacked one (deformation.cdl, plain float32, no scale_factor), produced by the same reference tool. This format makes packing mandatory instead -- displacement is always int32 with a scale_factor, never plain float -- rather than leaving that choice open the way GGXF itself does. Nothing in this format's own schema needs to know whether a given grid's own displacement values represent a literal rate or a dimensionless multiplier on its layer's own summed time functions -- that choice belongs entirely to whatever tool generates the grid, and is never read or interpreted at query time beyond "raw stored integer times this attribute."

This layer's own time-varying behaviour, shared by every scalar_with_time_function grid nested within it, is timeFunctions (see "Time functions" above), adopting GGXF's own named-shape mechanism directly (see "GGXF time function shapes" above). The existing model's own three real component shapes map onto it exactly: velocity -> a single linear entry with no bound, extrapolating in both directions forever; step -> a single step entry; ramp -> a single ramp entry. A linear entry whose own startDate equals its own functionReferenceDate instead contributes exactly zero before that date (see "GGXF time function shapes" above), reproducing a delayed-onset velocity -- not needed by any real existing component, but representable directly. A real patch needing more than one physical contribution summed maps onto more than one entry -- the Dusky Sound earthquake (coseismic step plus postseismic decay) is exactly this, matching GGXF's own published encoding of that same event: timeFunctions.count = 2, two summed ramp entries, one zero-width (degenerating to a step). No component of the existing NZGD2000 deformation model data needs a shape outside velocity/step/ramp -- the other six shapes in "GGXF time function shapes" above are declarable but currently unused.

has_end_day/own_end_date (see "Terminal-node evaluation" below) exist here too, but as a single grid-wide pair, not per-node -- there is only one shared time series to end. Setting them therefore ends the grid's contribution everywhere at once; there is no way to end it over only part of the grid's own footprint. This matches how the LINZDEF format already works: its only revocation mechanism retires an entire named component as of a version, never a footprint within one -- so this is not a reduction in capability relative to what exists today, only a name for behaviour that format already has. A footprint narrower than a grid's own full extent that genuinely needs its own independent end date has to be its own separate, smaller grid (via "Grid resolution within a layer" above) or a "ragged segments" grid, either of which supports it directly.

has_end_day is stored as a length-1 dataset (variable), not a netCDF attribute -- for consistency: the identically-named field is already a per-node dataset on "ragged segments" (see "Per-node ragged segment storage" below), so storing it as an attribute here would force a reader to have two different read mechanisms for the same field name depending on a grid's own grid_type. own_end_date, by contrast, is deliberately a different field from "ragged segments"' own own_end_day -- not just a different value, a different name and a different representation (an ISO-8601 date-time attribute here, versus a per-node day-count array there) -- because the two have genuinely different cardinality: one value per grid here, one value per node there. A reader already has to know a grid's own grid_type before it knows which field name to look for at all, so there is no "two mechanisms, one name" ambiguity to avoid here the way there is for has_end_day.

Segment record

Applies only to ragged_segments grids -- scalar_with_time_function grids do not use this record type at all, see "Per-grid time function storage" above.

One segment record (compound type, 8 bytes, no padding):

Field Type Byte offset Scale Meaning
segment_start_value int32 0 0.01 mm/unit The node's total accumulated displacement, exactly at this segment's own start date.
day_delta uint16 4 1 day/unit Days after this node's own reference_day.
segment_scale_factor int16 6 depends on function_type_{enu} (see below) This segment's own named shape's scaleFactor (see "GGXF time function shapes" above, and this segment's own entry in function_type_{enu}, "Per-node ragged segment storage" below) -- for linear, this is exactly the rate of displacement change starting at this segment's own start date, continuing until the next segment (or indefinitely, for the last one).

segment_scale_factor's own scale varies by that record's own paired function_type_{enu} entry, mirroring how displacement/scale_factor (see "Per-grid time function storage" above) lets each grid state its own real-valued unit rather than fixing one universally: refFunc(Δ) itself is dimensionless or bounded for seven of the nine shapes (step/ramp/exponential/ logBaseE/logBase10/cyclic/hyperbolicTangent, see "GGXF time function shapes" above), so segment_scale_factor there is a plain amplitude, 0.01 mm/unit -- the same scale segment_start_value already uses. linear's own refFunc(Δ) = Δ is a rate, and Δ here is a day count (see "GGXF time function shapes" above), so its segment_scale_factor is 0.01/365.2425 mm/day/unit (see "Numeric ranges" below for why this specific granularity). quadratic's own refFunc(Δ) = Δ² needs segment_scale_factor in (0.01/365.2425) mm/day²/unit to keep the product dimensionally a displacement. This is a metadata-free convention, not a stored attribute -- exactly as scaleFactor's own units already vary silently by functionType on the GGXF/scalar side too (see "Per-grid time function storage" above), a reader is expected to already know a segment's own function_type_{enu} before reading segment_scale_factor, so no separate unit field is needed here either.

(Field order matters for byte alignment: the 4-byte field is placed first so it lands on an offset that is a multiple of 4 in every record, and since the whole record is 8 bytes -- itself a multiple of 4 -- this alignment holds consistently across the entire flat array.)

Each segment is equivalent to GGXF's own value = spatial-value × time-function model, shrunk to one point: segment_start_value plays the role of a trivial (one-node) spatial value, and this segment's own function_type_{enu} entry together with segment_scale_factor play the role of one named GGXF time function scaling it -- except segment_start_value is added plainly, after that time function evaluates, rather than forced through it. A single named function alone cannot carry an arbitrary nonzero starting value, only a shape relative to its own zero point -- and GGXF's own zeroing subtraction (refFunc(Δ) - refFunc(functionReferenceEpoch)) only fires when a functionReferenceEpoch is actually supplied; left absent, step's value at Δ = 0 is 1, not 0, and hyperbolicTangent's is 0.5 (see "GGXF time function shapes" above). Every ragged segment supplies one implicitly: its own start day, always. So each segment's own evaluation is segment_start_value + segment_scale_factor * (refFunc(Δ) - refFunc(0)) (see "Query evaluation, end to end" below), guaranteeing segment_start_value is exactly the value at this segment's own start day for every shape uniformly, not by relying on that being naturally true for seven of the nine and false for the other two. Composition across segments (finding the one currently-active segment for a node's own query time) stays this format's own selection mechanism, unrelated to this per-segment equivalence -- see the design note in "Per-node ragged segment storage" below for why GGXF's own summation-based composition does not transfer to that part.

Two fields that might seem obviously necessary are deliberately not included: an instantaneous "jump" size, and a raw "change in slope" delta at each segment. Both were considered and dropped: the evaluation procedure below never needs either one (only segment_start_value, day_delta, and segment_scale_factor are read), and both are exactly, losslessly recoverable by subtracting two adjacent records' own segment_start_value/segment_scale_factor if any future tool genuinely needs them.

Per-node ragged segment storage

"ragged segments", by contrast, is a grid whose "value" at each node is not a single number but a reference into a shared, layer-wide flat array of per-node time-series records. Has no grid-wide time function at all -- each node's own timing is fully described by its own records.

A node's own East/North[/Up] components share the same data span (the same underlying acquisitions feed all of them) and the same termination, if any (a location either continues to be modelled here or a newer source takes over there -- not an axis-specific fact). What genuinely differs per component is the fitted piecewise curve itself: East's own breakpoints, their count, and their values are generally different from North's or Up's, even within that same shared span. So reference_day/has_end_day/own_end_day below are each one shared array per node, while segment_count_{enu}/segments_{enu} are each one independent array per component (see "Format specification" above for the _{enu} notation).

Every field below is a layer-wide array: N here is the total node count across every grid in this layer, at every nesting depth (sum(iNodeCount * jNodeCount) over all of them -- see "Consolidated storage for ragged_segments grids" above), not one grid's own node count alone. grid_node_offset -- grid g's own slice into this shared N-length space, [grid_node_offset[g] : grid_node_offset[g+1]] -- is not a stored field: unlike segment_count_{enu} below (which has no other source, so it must be stored for its own offsets to be reconstructed from), a grid's own node count is already fully determined by that grid's own iNodeCount * jNodeCount ("Consolidated storage for ragged_segments grids" above), so storing a second, derived array on top would only duplicate it. A reader instead reconstructs grid_node_offset the same way it already reconstructs segment_count_{enu}'s own offsets below -- a one-time cumulative sum over grid, O(grid count), when the file is opened -- except summing iNodeCount * jNodeCount instead of a stored count:

grid_node_offset[0] = 0
grid_node_offset[g] = sum(iNodeCount[0..g-1] * jNodeCount[0..g-1])   for g > 0

grid_node_offset[grid count] (the array's own final entry) equals N exactly -- the same total, computed by the same sum. A grid's own local node_index (i * jNodeCount + j, "Grid spatial indexing attributes" above) becomes grid_node_offset[g] + node_index -- its own absolute position within N -- when used to index into any field below; every field otherwise keeps exactly the shape and meaning described here.

Name Kind dtype Shape Required Meaning
segment_count_e/segment_count_n[/segment_count_u] variable uint16 length N required, one per component for each node: the number of segment records belonging to it, for this component
reference_day variable uint32 length N required for each node: day count from that layer's own reference_date to its own first segment's start date -- shared across every component
has_end_day variable uint8 (0 = false, 1 = true) length N optional for each node: whether its own final segment has an explicit end date -- shared across every component (see "Terminal-node evaluation" below)

segment_ramp_end_delta_e/segment_ramp_end_delta_n[/segment_ramp_end_delta_u] variable uint16 length = count of ramp-coded entries in that component's own function_type_{enu} required, one per ramp-typed segment, absent otherwise for each ramp-typed segment, in the same relative order it appears in segments_{enu}/function_type_{enu}: day count after that segment's own day_delta at which its own rise to 1 completes

  • segment_count_{enu}: a node could in principle need up to 253 segments (one baseline segment, plus up to 252 break events assuming one slope-change and one step per year) across this format's design lifetime -- currently set as 2000-2026 plus another 100 years -- see "Numeric ranges" below -- and uint8's maximum of 255 would leave too little headroom, hence uint16.

  • A node with segment_count_{enu} = 0 for every component has no real data at all -- e.g. a lattice position that falls inside a grid's own rectangular extent without a real underlying fit. It contributes exactly 0 at every query date for every component (see "Query evaluation, end to end" below); reference_day still has to hold some stored value regardless (it's a per-node array with no way to omit one node), but since nothing ever reads it when every one of that node's own segment_count_{enu} is 0, its value is unconstrained -- a writer may store 0.

  • reference_day: every date within this node's own segment records, for any component, is expressed relative to this one shared value, not directly to that layer's own reference_date (see "Layer attributes" above). reference_date being a per-layer, not a per-node, value does not make reference_day redundant: reference_date is one value shared by an entire layer, however far in the past a writer picks it, while reference_day is a further per-node zero-point that keeps day_delta/own_end_day (both uint16, see "Numeric ranges" below) cheap regardless of how distant that layer's own reference_date is -- exactly the same reasoning "Numeric ranges" below already gives for widening reference_day itself to uint32 while leaving day_delta/own_end_day at uint16. Dropping reference_day and measuring day_delta/own_end_day straight from reference_date would force those two fields wider too, to cover the same distant-reference_date case -- so reference_day earns its keep independent of where reference_date itself lives.

  • has_end_day: absent by default.

  • own_end_day: ignored where has_end_day is false.

  • segments_{enu}: each node's own records for this component sorted by date ascending. Node node_index's own slice is segments_{enu}[offset : offset + segment_count_{enu}[node_index]], where offset is the sum of segment_count_{enu} for every node before it (the standard CSR (Compressed Sparse Row)/ragged-array offset reconstruction -- not stored directly, computed once per component from its own segment_count_{enu}, when the file is opened).

    segment_count_{enu} stores counts rather than offsets deliberately, matching CF's own documented ragged array representation. Each component's own offset is reconstructed from its own segment_count_{enu} as

    offset[0] = 0
offset[n] = sum(segment_count[0..n-1])   for n > 0

    i.e. each node's own starting position is the running total of every earlier node's own count, not including its own -- a plain (unshifted) cumulative sum would instead give each node's own ending position, one past the end of its own slice. This reconstruction is a one-time O(N) pass per component when the file is opened, not a per-query cost.

  • function_type_{enu}: walks in lockstep with segments_{enu} -- same length, same per-node slice via the same segment_count_{enu}-derived offsets above, no separate indexing of its own. function_type_{enu}[offset + i] is the named shape for segments_{enu}[offset + i].

  • segment_ramp_end_delta_{enu}/segment_time_param_{enu}: sparse, and discriminated by function_type_{enu} rather than by node -- the same CSR-style trick segment_count_{enu} above already uses to avoid storing offsets directly, just keyed by a segment's own type instead of by which node it belongs to. linear/step/quadratic need neither array at all: refFunc(Δ) for all three is fully determined by Δ and segment_scale_factor alone (see "GGXF time function shapes" above), so those segments never consume an entry from either one, and a file with no other shape declares both arrays at length 0. A reader reconstructs each segment's own direct offset into whichever sparse array applies (or "none") once per component, when the file is opened, by walking function_type_{enu} in its existing order and consuming the next unused entry of segment_ramp_end_delta_{enu} on every ramp code, or of segment_time_param_{enu} on every exponential/logBaseE/logBase10/cyclic/hyperbolicTangent code -- an O(sum(segment_count_{enu})) pass per component, the same cost class as the existing segment_count_{enu} offset reconstruction above, not a per-query cost. This mirrors how a base class's common fields relate to a derived class's own extra field stored out-of-line: every segment always carries segment_start_value/day_delta/segment_scale_factor/ function_type_{enu} (its "base" fields, see "Segment record" above), and only a segment whose own type genuinely needs more pays for the extra value, discriminated by that same type tag it already carries.

See "Segment record" above for the compound type each record in segments_{enu} holds (segment_start_value/day_delta/segment_scale_factor), "GGXF time function shapes" above for what each record's own paired function_type_{enu} entry means, and segment_ramp_end_delta_{enu}/segment_time_param_{enu} above for the one extra parameter six of those nine shapes need beyond what "Segment record" above stores.

At query time, exactly one segment is found (via the count/offset lookup above) and evaluated -- no other segment is touched. This is mathematically equivalent to GGXF's own CompoundTimeFunction, not a different rule: each earlier segment can be thought of as its own term that contributes its own local growth while active, then freezes at its own completed value forever after -- exactly GGXF's endEpoch-clamp behaviour, which matches this format's own has_end_day/own_end_day semantics. Summing every such frozen earlier term at any later time gives a constant, and that constant is exactly segment_start_value, computed once when the record is written rather than summed live at every query. Only the currently active segment's own term is still genuinely time-varying, so only it needs evaluating live; every earlier one has already collapsed into the single cached number segment_start_value carries. Doing this live -- walking and summing a growing list of terms as a node accumulates real breakpoints, up to 252 in the worst case (above) -- would violate requirement 2; caching the sum in advance is what keeps this an O(1) lookup, not a different composition rule.

Terminal-node evaluation (what happens after a node's own last segment)

A node's final segment -- its own last (most recent) one, for "ragged segments", or the sum of its own layer's timeFunctions, for "scalar with time function" -- continues to apply indefinitely into the future by default, there is no implicit assumption that motion stops or slows down. It stops being extrapolated only where has_end_day is true and the query point in time is past that grid's own end point -- for "scalar with time function" grids, own_end_date, an ISO-8601 date compared directly against the query's own date (see "Per-grid time function storage" above); for "ragged segments" grids, reference_day + own_end_day, a day count compared against query_day in that layer's own reference_date-relative unit (see "Per-node ragged segment storage" above and "Query evaluation, end to end" below) -- at which point the value is held fixed at whatever it had reached -- it does not reset to zero, and does not keep changing.

This single pair of fields -- has_end_day plus own_end_date (scalar) or own_end_day (ragged) -- does double duty as the mechanism for both requirement 6 (deliberate, non-default early termination) and requirement 7 (temporal supersession) -- the two differ only in who sets them, and when, not in how a reader evaluates them:

  • For requirement 6, the grid's own layer sets them itself, at generation time, wherever there is a specific physical reason (e.g. an expected post-seismic decay) to expect that grid's own motion to subside by a known date.
  • For requirement 7 (temporal supersession -- one layer replacing another over a specific footprint from a specific date, e.g. a ground survey taking over from InSAR where InSAR has no valid measurement at all), the superseding layer's own creation is what sets has_end_day and its own end-point field on the layer it replaces -- for "scalar with time function" grids, own_end_date set directly to the superseding layer's own start date (both are already plain ISO-8601 dates, so no conversion is needed); for "ragged segments" grids, own_end_day computed as the number of days between that node's own reference_day and the superseding layer's own start date. This is a narrow, deliberate mutation of an already-published layer's file, performed only when a new layer is specifically created to supersede part or all of an existing one -- an ordinary new layer with no such relationship to any existing layer never touches another layer's file at all (see requirement 11, "Append-only extensibility", above). The footprint itself is exactly the superseding layer's own grid extent -- the same containment test used in "Grid resolution within a layer" above, applied to the superseded layer's own nodes -- not a separately authored shape. What exactly gets touched depends on the superseded layer's own grid type: for "ragged segments", only the node_index values the superseding layer's own grid extent covers (the fields are per-node, so this is genuinely partial); for "scalar with time function", the single grid-wide pair, meaning the entire grid ends at once -- a superseding layer can only fully replace a whole scalar grid, never carve out part of one (see "Per-grid time function storage" above). The superseding layer's own creation also records itself as the reason, via its own supersedes attribute naming the layer it replaced (see "Layers and grids" above) -- write-once, purely for provenance, and not itself consulted by query evaluation.

No separate cross-layer declaration or lookup is needed at query time: by the time a reader evaluates the superseded layer, has_end_day and its own own_end_date/own_end_day already fully describe where it stops, exactly as they would for an ordinary, self-authored early termination -- supersedes exists so a later reader can additionally answer why and by what, not to drive evaluation itself.

This mechanism only ever touches the superseded layer's own discrete nodes (via containment, see above) -- it says nothing about query points that fall between a touched and an untouched node. This only affects "ragged segments" grids, since that is the only grid type where has_end_day/own_end_day is per-node rather than grid-wide. Where the superseding layer's own grid resolution or extent doesn't align with the superseded grid's own node spacing, a superseded-layer grid cell can end up with some corners touched (has_end_day set) and others not. A query point in that cell but outside the superseding layer's own extent is evaluated entirely within the superseded layer -- bilinearly interpolating a mix of corners frozen at their pre-supersession values and corners still evaluating normally at the true query_day -- rather than continuing unaffected, even though the point itself is outside the superseding layer's coverage.

This is a limitation of the format's own design, not something query evaluation is required to resolve. The two options below are optional implementation-side workarounds, not part of the specification itself -- a compliant reader is not required to implement either.

  1. When creating a superseding layer, re-sample its own grid to align with the superseded layer's own existing node lattice, so the superseding layer's own extent boundary always falls exactly on one of the superseded layer's own node positions, rather than choosing the superseding grid's own resolution and extent independently. Done this way, no superseded-layer grid cell ever ends up with a mix of touched and untouched corners.
  2. For a layer that already has nested child grids each with potentially different spacing/alignment: when a corner's own value is frozen (past its own own_end_day), before accepting that frozen value, check whether that corner's own real-world position also satisfies the containment check from "Grid spatial indexing attributes" above against a more deeply nested grid within the same layer -- a child, or a descendant further down the same nesting chain -- that can supply a live, non-frozen value there via its own bilinear interpolation. Use that live value instead if one is found, recursing into further nestings as needed; only fall back to the frozen cap value if no nested grid anywhere below can supply a live replacement. This means the 4 corners bilinearly interpolated for one query point can end up sourced from different grids within the same layer, not necessarily all 4 from the grid the query point itself resolved to.

"Scalar with time function" grids don't have this failure mode: has_end_day/own_end_date is grid-wide there, so every corner of one bilinear interpolation always shares the same frozen-or-not state -- there is no mixed cell to blend across. That grid type has a different limitation instead, already noted in "Per-grid time function storage" above: a superseding layer can only end a whole scalar grid at once, never carve out part of one.

Query evaluation, end to end

To evaluate one layer's own contribution at an arbitrary (longitude, latitude, date), both grid types compute Δ the same way: a real day-count difference, with no year-length conversion anywhere (see "GGXF time function shapes" above and "Where this format departs from GGXF, and why" above for why) -- they differ only in where that day count comes from, each following directly from how each type stores its own dates (see "Time functions", "Per-grid time function storage", and "Per-node ragged segment storage" above):

  • "scalar with time function" grids compare date directly against the ISO-8601 date-time fields already stored on the grid itself (own_end_date) or its own layer (each timeFunctions.<n>'s own date attributes), taking the real day-count difference between the two strings involved at query time -- no single shared reference_date is needed, since each timeFunctions.<n> entry already carries whichever date field its own shape requires.
  • "ragged segments" grids first convert date into query_day: the number of days from that layer's own reference_date attribute (see "Layer attributes" above) to date -- the same day-count-since-reference_date unit as reference_day, day_delta, and own_end_day below. Every ragged step below works only in that unit; reference_date itself is not touched again after this one conversion. Its own reference_day/day_delta are already stored as this exact day count, so no further date-string parsing happens at query time at all.

segment_scale_factor and timeFunctions.<n>.scaleFactor (for linear specifically -- every other shape's scaleFactor is a dimensionless amplitude, see "GGXF time function shapes" above) are both declared per day (see "Segment record" and "Numeric ranges" below), matching Δ directly -- no conversion is needed at multiplication time either, for either grid type.

The steps below cover the ordinary case of a single grid's own 4 corners evaluated independently and bilinearly interpolated -- i.e. interpolationMethod = "bilinear" (see "Time functions" above); "bicubic"/"biquadratic" use a different, wider node neighbourhood entirely and aren't specified here (see "Grid spatial indexing attributes" above). They also do not cover the more complicated case of a query point falling between a superseding grid's own boundary and one of the superseded grid's own node positions -- see "Terminal-node evaluation" above for that edge case.

  1. Resolve the layer to a single grid at this point via "Grid resolution within a layer" above (trivial -- there is exactly one candidate -- for the common single-grid layer). If no grid covers the point, the layer's contribution is 0 and the steps below are skipped entirely.

For that resolved grid, if it's "scalar with time function":

  1. For each parameter this layer's own gridParameters declares independently: find the 4 corner nodes' own displacement values for that parameter (each raw stored integer multiplied by that grid's own scale_factor attribute to recover its real value) and bilinearly interpolate them.
  2. Compute t_eval = min(date, own_end_date if has_end_day else +infinity), comparing ISO-8601 date-times directly -- see "Terminal-node evaluation" above for how has_end_day/own_end_date come to be set, including by a superseding layer's own creation. Then evaluate each of this grid's own layer's timeFunctions.<n> entries at t_eval, computing each entry's own Δ as the real day-count difference between t_eval and whichever date field that entry's own shape requires (per "GGXF time function shapes" above), and sum them per the formulas there.
  3. Multiply each parameter's own interpolated displacement value from step 1 by the same summed value from step 2 (shared across every parameter this layer declares) to get the grid's (and hence the layer's) contribution to that parameter.

For that resolved grid, if it's "ragged segments" instead:

  1. Use the grid's own affineCoeffs/iNodeCount/jNodeCount to find the 4 grid nodes (corners) surrounding the query point, and the bilinear interpolation weights for each, exactly as for an ordinary scalar grid. Also convert date into query_day (above) -- once per query, using this layer's own reference_date, not once per corner.

  2. For each of the 4 corner nodes independently:

    1. Compute t_eval = min(query_day, reference_day + own_end_day if has_end_day else +infinity), using that node's own reference_day/has_end_day/own_end_day -- these are shared across every component (see "Per-node ragged segment storage" above), so this is computed once per node, not once per component.
    2. For each component (_{enu}) independently, using that same t_eval: within that node's own segment records for this component (segment_count_{enu}[node_index] records, starting at its own computed offset into that component's own segments_{enu} array), find the last record whose own absolute day (reference_day + day_delta) is at or before t_eval. If no such record exists -- either because segment_count_{enu}[node_index] is 0 (this node has no real data for this component at all, see "Per-node ragged segment storage" above), or because t_eval is before reference_day (i.e. before the node's own first segment, which always starts exactly at reference_day, day_delta = 0) -- this node's value for that component is 0.
    3. Otherwise, that node's value for this component is segment_start_value + segment_scale_factor * (refFunc(Δ) - refFunc(0)), where Δ = t_eval - that_record's_own_absolute_day and refFunc is whichever shape that record's own paired function_type_{enu} entry declares (see "GGXF time function shapes" above) -- e.g. for linear, refFunc(Δ) - refFunc(0) = Δ - 0 = Δ, giving segment_start_value + segment_scale_factor * Δ directly, unchanged from a naive refFunc(Δ) reading since linear's own refFunc(0) = 0 already. Every shape's own Δ = 0 exactly at that record's own start (day_delta measures days after reference_day, and t_eval at a segment's own start day gives Δ = 0 by construction), so refFunc(Δ) - refFunc(0) is exactly 0 there regardless of shape, matching "Segment record" above's own zero-at-start argument for every shape uniformly, not just linear.

    ramp/exponential/logBaseE/logBase10/cyclic/hyperbolicTangent each need their own extra parameter beyond segment_scale_factor -- ramp its own end offset, exponential/logBaseE/logBase10/hyperbolicTangent their own timeConstant, cyclic its own frequency (see "GGXF time function shapes" above) -- which live in the sparse segment_ramp_end_delta_{enu}/segment_time_param_{enu} arrays (see "Per-node ragged segment storage" above), not in the base "Segment record" above. A reader looks that record's own extra value up, if its own function_type_{enu} needs one, via the direct offset already reconstructed once per component when the file was opened (see "Per-node ragged segment storage" above) -- an O(1) lookup at query time, same as every other step here. For ramp specifically, its own end offset is a day count after that record's own day_delta, so Δ_end = segment_ramp_end_delta_{enu}[...] directly, already in the same day-count unit as Δ itself, and refFunc(Δ) = 0 if Δ < 0; Δ / Δ_end if 0 ≤ Δ < Δ_end; 1 if Δ ≥ Δ_end -- generalising "GGXF time function shapes" above's own single-Δ ramp formula to ragged's own two-epoch (start, end) storage. For the other five, refFunc(Δ) reads directly off segment_time_param_{enu}[...] as that record's own timeConstant or frequency, per the formulas in "GGXF time function shapes" above, with no further conversion needed.

  3. For each component independently, bilinearly interpolate the 4 corner nodes' own computed values for that component, using the weights from step 1.

The total deformation at (longitude, latitude, date) is the sum of every layer's own independently computed contribution (cross-layer summation, unchanged from the LINZDEF model's own architecture) -- each layer contributing the single value its own grid-resolution step above selected, never a sum of that layer's own internal candidate grids.

Numeric ranges (why these specific types and scales)

  • day_delta and "ragged segments"' own own_end_day as uint16, 1 day/unit: maximum representable span is about 179 years, comfortably covering this format's stated 126-year design requirement (the year 2000 through 2126) with headroom. This reasoning holds regardless of how far in the past reference_date itself is chosen, since both fields are relative to a node's own reference_day (below), not to reference_date directly.
  • "ragged segments"' own reference_day as uint32, not uint16: unlike day_delta/ own_end_day above, reference_day is directly relative to reference_date, so a distant reference_date (e.g. "1970-01-01", this document's own illustrative example in "Container" above) genuinely narrows its headroom -- 1970 to 2126 is already within about 8,500 days of uint16's own maximum. uint32's own range (millions of years) makes the choice of reference_date irrelevant to this field's own headroom, at the cost of 2 extra bytes -- cheap, since reference_day is a standalone per-node variable, not a compound-record field, so widening it has no knock-on effect on any other field's own byte layout.
  • segment_count_{enu} as uint16: this format must support at least one discontinuous jump and one gradual rate change per year (two independent break events), across the full 126-year window -- up to 252 break events, plus the one baseline segment every node starts with regardless of how many (if any) break events it ever has -- 253 segments for a single node in the worst case. uint8 (maximum 255) was considered and rejected: it would leave only 2 values of headroom against that real requirement.
  • segment_start_value as int32, 0.01mm/unit: an int16 field at that same 0.01mm/unit scale maxes out at only about 0.33 metres (32767 * 0.01mm), nowhere near wide enough -- a typical secular rate of tens of mm/year accumulated over 126 years alone can exceed 3 metres of total displacement, without even counting large earthquake jumps.
  • displacement as int32, same reasoning and scale as segment_start_value above (int16 would be too narrow for the same reason). Real int32-packed displacement data uses only a small fraction of the type's own range: ~300,000 raw units for 3 metres at 0.01mm/unit, against int32's own ~2.1 billion -- several thousand-fold headroom, comfortably safe against both this format's own displacement magnitudes and the reserved missing_value/noDataFlag sentinel (2147483647, int32's own maximum value, see "Parameters" above) never colliding with a real packed value.
  • segment_scale_factor as int16, raw value r (range -32768..32767) recovered as r × 0.01/365.2425 mm/day for linear (mm/day² for quadratic, plain mm for the other seven bounded/dimensionless shapes -- see "Segment record" above for why the unit itself varies by function_type_{enu}; 365.2425 here is purely how this specific granularity is stated in familiar terms, not a year-length convention used anywhere in evaluation, see "Where this format departs from GGXF, and why" above): this specific granularity, 0.01/365.2425 ≈ 0.0000274 mm/day per raw unit (not the ten-times-coarser 0.1/365.2425 ≈ 0.000274 that might seem adequate at first), is reasoned here for linear specifically, since only its own uncompounded rate gets multiplied by however many raw days have elapsed since the segment's own start (Δ, itself a raw day count, can be up to 126 × 365.2425 ≈ 46020 at this format's own 126-year design horizon), so a rounding error of up to half a raw unit in the stored rate compounds with elapsed time rather than staying fixed. At the chosen granularity, that worst case is 0.5 × 0.0000274 × 46020 ≈ 0.63mm -- well under the deformation model's own accuracy target (about 10mm). At the ten-times-coarser granularity, the same calculation gives ≈ 6.3mm -- a large fraction of that target -- which is why the finer granularity is chosen instead. Range check, independent of the granularity choice above: the maximum representable rate, 32767 × 0.0000274 ≈ 0.897 mm/day (≈ 327.67 mm at this granularity's own 365.2425-day reference span), comfortably covers this format's own real target magnitudes -- typical secular rates of tens of mm/year, and postseismic rates of a similar order. The other two scale variants keep the same granularity for one consistent int16field across every shape, not because either has its own compounding argument --quadratic's own Δ²and the seven bounded shapes' own boundedrefFunc` don't accumulate rounding error against elapsed time the way an uncompounded rate does.
  • function_type_{enu} as uint8: nine real values (see "GGXF time function shapes" above), nowhere near needing more than one byte.
  • segment_ramp_end_delta_{enu} as uint16, 1 day/unit: the same headroom reasoning as day_delta/own_end_day above -- it too is a day count relative to a segment's own start, not to a distant reference_date directly (see "Per-node ragged segment storage" above).
  • segment_time_param_{enu} as float64, not a scaled integer: the same reasoning as timeFunctions.<n>.scaleFactor/.timeConstant/.frequency above -- sparse, one value per segment that actually needs it (currently none, see "Per-node ragged segment storage" above), not one per segment unconditionally, so the compounding-precision argument that justifies segment_scale_factor's own scaled-integer encoding above does not carry over; GGXF's own shipped files store timeConstant/frequency as plain floats too.
  • own_end_date (per-grid) and timeFunctions.<n>.functionReferenceDate/.startDate/.endDate/.eventDate (per-layer) as ISO-8601 date-time strings, not scaled integers: the same reasoning as timeFunctions.<n>.scaleFactor/.timeConstant/.frequency above -- these are rare attributes (one value per grid for own_end_date, a handful per layer for timeFunctions.<n>.*), not one per node or segment, so the compactness argument that justifies day_delta/own_end_day's own scaled-integer encoding above does not apply. Δ is computed from these strings the same day-count-based way as for ragged_segments (see "Query evaluation, end to end" above), so unlike reference_day/day_delta, there is no separate storage-format distinction here to motivate a different (scaled-integer) type.
  • timeFunctions.count as uint8: no real layer needs more than a handful of summed entries (the Dusky Sound earthquake, the most complex real case, needs 2) -- GGXF's own reference implementation uses an unwidthed list with no declared maximum, so there is no GGXF convention to match here; uint8 is this format's own choice, the same "no wider than necessary" reasoning already applied to gridPriority/iNodeCount/jNodeCount elsewhere in this document.
  • timeFunctions.<n>.scaleFactor/.timeConstant/.frequency as float64, not scaled integers: unlike segment_scale_factor (a per-segment array, where compactness matters at scale), these are rare per-grid attributes -- a handful of values per file, not one per node or segment -- so the compounding-precision argument that justifies scaled integers elsewhere does not apply, and GGXF's own shipped files store these as plain floats too.

displacement is deliberately not derived the same way: its own range depends on how a given grid's author defines its shared segment sequence's own magnitude (see "Layers and grids" above), which this specification does not fix -- so instead of one universal scale, each grid states its own via the scale_factor attribute, exactly as today's writer already assigns one resolution value per grid rather than deriving a single constant that would have to fit every grid this format will ever hold.

segment_start_value/day_delta/segment_scale_factor (0.01mm, 1 day, 0.01/365.2425 mm/day|mm/day²|mm depending on function_type_{enu}, see "Segment record" above) -- "ragged segments"' own compound-type record -- are stored as pre-scaled integers with the scale documented here, not via netCDF-4's own scale_factor/add_offset attribute convention. For compound-type variables, while the netCDF4 Python library accepts scale_factor/add_offset attributes without error, it silently fails to apply them on readback -- values come back as the raw stored integers, not unscaled floats. Using the convention here would therefore not just be unsupported but actively misleading (a reader could see the attributes present and wrongly assume unscaling had already happened). It would also be structurally the wrong shape for this record regardless: one scale_factor/add_offset pair covers a whole variable, but the three fields each need their own independent scale.

This does not apply to displacement, own_end_day, or function_type_{enu} -- each a plain (non-compound) variable, where the convention works correctly. displacement does use it (scale_factor, see "Per-grid time function storage" above) -- GGXF's own standard netCDF packing convention, as used by GGXF's reference writer, not something this format invented (see "Per-grid time function storage" above for GGXF's own shipped files packing optionally rather than always, and this format making it mandatory instead).

Terminology

HDF5

Hierarchical Data Format, version 5: a general-purpose binary container format for large, structured scientific data -- groups (like folders), datasets (typed n-dimensional arrays), and attributes (small metadata key/value pairs) attached to either.

netCDF-4

A higher-level data model and file format built on top of HDF5, widely used in earth-science data exchange. A netCDF-4 file is an HDF5 file, following additional internal conventions that make it readable by generic netCDF tooling, not just raw HDF5 tools. ("netCDF" itself stands for "network Common Data Form".)

CF

Climate and Forecast conventions: a community metadata standard (cfconventions.org) for netCDF files. Despite the name (it originated in climate/weather modelling), this format only uses its general-purpose ragged array representation.

Ragged array representation

A CF convention for storing a collection of "features" (here: nodes), each with a different number of associated records (here: segments), using only ordinary fixed-size arrays: one flat array holding every feature's records concatenated together, plus a small per-feature "count" array giving how many records belong to each one. The same underlying idea as CSR.

CSR

Compressed Sparse Row: a standard sparse-matrix/ragged-data storage layout (the name is from sparse linear algebra, unrelated to earth science): a flat array of all real values back-to-back, plus an "offsets" array where offsets[i+1] - offsets[i] gives element i's own count, and data[offsets[i]:offsets[i+1]] is its own slice of the flat array. This document uses "CSR" for the storage layout and "the count/offset arrays" for the concrete fields.

VLEN

Variable-length type: a netCDF-4/HDF5 data type where each array element is itself a variable-length list. Considered and rejected for this format's ragged storage in favour of the ragged array representation -- VLEN data is stored as separately heap-allocated blobs rather than one contiguous array, which generally compresses and chunks worse.

Compound type

A netCDF-4/HDF5 data type combining several fields into one fixed-size record, analogous to a C struct or a database row.

GGXF

Gridded Geodetic data eXchange Format: a standard (specification OGC-22-051r7) published by the OGC (Open Geospatial Consortium) for exchanging gridded geodetic data, including deformation models, built on netCDF-4.

GTG

Geodetic TIFF Grids: a PROJ/OSGeo specification for storing geodetic grids inside ordinary GeoTIFF image files -- a different format from GGXF, and the one PROJ actually uses in its own, currently-deployed deformation model.

Bilinear interpolation

The standard method for estimating a value at an arbitrary point inside a rectangular grid cell from the 4 known values at that cell's own corners, weighted by how close the point is to each corner.

Bicubic interpolation

A higher-order method for estimating a value at an arbitrary point from a wider neighbourhood of surrounding nodes than bilinear interpolation uses, fitting a smoother surface through them.

Biquadratic interpolation

Similar to bicubic interpolation, but fitting a lower-order surface through a smaller surrounding neighbourhood of nodes.
